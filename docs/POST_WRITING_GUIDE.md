## 파일 구조

새 프로젝트를 추가할 때는 다음 구조를 따라주세요:

```
content/projects/
  project-slug/          # 프로젝트 식별자 (URL에 사용됨)
    index.mdx           # 필수: 프로젝트 상세 설명
    privacy.mdx         # 선택: 개인정보처리방침 (앱인 경우)
```

### 프로젝트 slug 규칙
- 소문자와 하이픈(-)만 사용
- 영문으로 작성 (예: `belief-changer`, `hang-on`)
- 프로젝트명을 간결하게 표현

## Frontmatter 작성

`index.mdx` 파일 상단에 다음 형식의 frontmatter를 작성합니다:

```yaml
---
title: "프로젝트 제목"
description: "프로젝트에 대한 한 문장 설명 (간결하게)"
category: "카테고리"
thumbnail: "/images/projects/파일명.png"
---
```

### 필드 설명

#### `title` (필수)
- 프로젝트의 정식 제목
- 한글 또는 영문 사용 가능
- 예시: `"Belief Changer"`, `"천원 쓰레기통"`, `"Hang On - 감정 공유 플랫폼"`

#### `description` (필수)
- 프로젝트를 한 문장으로 설명
- 메인 페이지의 프로젝트 카드에 표시됨
- 50-100자 정도가 적당
- 예시:
  - `"확언(Affirmation)을 AI 대화로 변환하여 TTS로 들려주는 믿음 재학습 웹 앱"`
  - `"80년대 아케이드 감성의 레트로 러너 게임"`

#### `category` (필수)
- 프로젝트 유형을 나타내는 카테고리
- 기존 카테고리:
  - `"Web"` - 웹 애플리케이션
  - `"Mobile"` - 모바일 앱
  - `"Game Development"` - 게임
  - `"Web Development"` - 웹 개발 도구
- 새로운 카테고리 추가 가능 (예: `"Desktop"`, `"Library"`)

#### `thumbnail` (선택)
- 프로젝트 썸네일 이미지 경로
- 경로: `/images/projects/파일명.png` 또는 `.jpg`
- 이미지가 없으면 프로젝트 제목의 첫 글자가 자동으로 표시됨
- 권장 크기: 1200x630px (16:9 비율)
- 예시: `"/images/projects/belief-changer.png"`

## 본문 구조

프로젝트 본문은 다음 섹션들로 구성됩니다. 섹션 제목은 `##`(h2)를 사용합니다.

### 1. 프로젝트 개요 (필수)
```markdown
## 프로젝트 개요

프로젝트가 무엇인지, 왜 만들었는지, 핵심 가치가 무엇인지 설명합니다.
```

**포함할 내용:**
- 프로젝트가 해결하는 문제
- 핵심 콘셉트 또는 차별점
- 간단한 배경 스토리 (있다면)
- 프로젝트의 목표 사용자
- 현재 상태 (완성도, 배포 여부)

**예시:**
```markdown
Belief Changer는 사용자가 입력한 확언(affirmation)을 여러 사람의 대화 형태로
변환하고, 이를 TTS(Text-to-Speech)로 들려주는 웹 애플리케이션입니다.
인지과학의 자유 에너지 원리(Free Energy Principle)를 기반으로, 반복적인
청각 입력을 통해 믿음 체계를 점진적으로 재구성하는 것을 목표로 합니다.
```

### 2. 기술 스택 (필수)
```markdown
## 기술 스택

또는

## 기술 스택 및 아키텍처
```

**포함할 내용:**
- 사용한 주요 프레임워크/라이브러리와 버전
- **왜** 그 기술을 선택했는지 (중요!)
- 기술적 아키텍처 개요
- 각 기술의 역할과 장점

**작성 팁:**
- 단순 나열이 아닌, 선택 이유를 설명
- 다른 기술과 비교하여 왜 이것을 선택했는지 명시
- 해당 기술이 프로젝트에 어떤 이점을 제공했는지 구체적으로 설명

**예시:**
```markdown
### 프론트엔드 프레임워크

React 19를 채택하여 최신 Concurrent 기능과 개선된 Suspense를 활용했습니다.
특히 React 19의 새로운 훅들과 자동 배칭(automatic batching)은 TTS 재생 중
상태 업데이트의 성능을 크게 개선했습니다.

### 상태 관리

Zustand를 상태 관리 라이브러리로 선택했습니다. Redux에 비해 보일러플레이트가
적고, Context API보다 성능이 우수하며, 특히 여러 스토어를 분리하여 관리하기
용이합니다.
```

### 3. 주요 기능 (필수)
```markdown
## 주요 기능

또는

## 핵심 기능
```

**포함할 내용:**
- 프로젝트의 핵심 기능 3-5개
- 각 기능의 동작 방식
- 사용자 관점에서의 가치
- 구현 세부사항 (간략하게)

**작성 팁:**
- 각 기능은 `###`(h3) 소제목으로 구분
- 사용자가 실제로 사용하는 플로우 중심으로 설명
- 필요시 스크린샷이나 예시 포함

**예시:**
```markdown
### 확언 관리

사용자는 변화시키고 싶은 믿음을 확언 형태로 입력합니다. 예를 들어
"나는 자신감 있게 발표한다", "나는 새로운 사람들과 쉽게 친해진다" 같은
문장을 작성할 수 있습니다. 입력된 확언은 로컬 스토리지에 저장되어
브라우저를 닫아도 유지됩니다.
```

### 4. 개발 과정 (필수)
```markdown
## 개발 과정

또는

## 개발 과정 및 의사결정

또는

## 개발 과정 및 기술적 결정
```

**포함할 내용:**
- 프로젝트 설계 과정
- 구현 단계별 진행 사항
- 직면한 기술적 도전 과제
- 문제 해결 방법
- 중요한 의사결정과 그 이유

**작성 팁:**
- 시간 순서대로 작성하면 이해하기 쉬움
- 실패한 시도와 개선 과정도 솔직하게 기록
- "왜" 이렇게 했는지 항상 설명
- 단순한 기능 구현보다는 도전과 해결에 집중

**예시:**
```markdown
### TTS Provider 통합

가장 도전적이었던 부분은 여러 TTS Provider를 통합하는 것이었습니다.
각 서비스마다 API 형태, 인증 방식, 응답 포맷이 달랐기 때문입니다.
이를 해결하기 위해 공통 인터페이스(`TTSProvider`)를 정의하고, 각 Provider가
이를 구현하도록 했습니다.
```

### 5. 결과 및 향후 계획 (필수)
```markdown
## 결과 및 향후 계획

또는

## 성과 및 개선 사항

또는

## 프로젝트 성과
```

**포함할 내용:**
- 프로젝트를 통해 달성한 것
- 배운 점과 성장한 부분
- 향후 개선하고 싶은 기능
- 아쉬운 점이나 개선 방향

**작성 팁:**
- 구체적인 성과 지표가 있다면 포함 (성능, 사용자 수 등)
- 기술적 학습뿐만 아니라 개인적 성장도 언급
- 향후 계획은 실현 가능한 것 위주로

**예시:**
```markdown
프로젝트의 핵심 목표였던 "확언을 대화로 변환하여 TTS로 재생하는 것"을
성공적으로 구현했습니다. Gemini AI가 생성하는 대화의 품질이 기대 이상이었고,
다중 TTS Provider 지원으로 사용자에게 선택권을 제공했습니다.

향후에는 대화 생성 품질을 더욱 개선하고, 사용자가 화자 성격을 직접 설정할 수
있는 기능을 추가할 계획입니다.
```

### 6. 링크 (선택)
```markdown
## 링크

또는

## 프로젝트 링크
```

**포함할 내용:**
- GitHub 저장소 링크
- 라이브 데모/배포 URL
- 관련 문서나 블로그 포스트

**예시:**
```markdown
## 링크

- **저장소**: [GitHub](https://github.com/qlsjtmek2/belief-changer)
- **라이브 데모**: [GitHub Pages](https://qlsjtmek2.github.io/belief-changer/)
```

### 추가 섹션 (선택)

프로젝트 특성에 따라 다음과 같은 섹션을 추가할 수 있습니다:

- **이론적 배경**: 프로젝트의 이론적 기반 (예: 자유 에너지 원리)
- **UX 설계 원칙**: 사용자 경험 설계 철학
- **디자인 시스템**: 디자인 패턴 및 스타일 가이드
- **성능 최적화**: 성능 개선 과정
- **테스트 및 품질 관리**: 테스트 전략
- **배포 및 운영**: 배포 프로세스, CI/CD

## 작성 스타일

### 깊이와 상세함
- **피상적인 설명 지양**: "React를 사용했다"가 아니라 "React를 선택한 이유와 어떤 이점이 있었는지" 설명
- **구체적인 예시 포함**: 추상적 설명보다는 실제 코드 예시나 사용 시나리오 제시
- **숫자와 지표 활용**: 성능 개선, 코드 커버리지, 사용자 피드백 등 구체적 수치

### "왜"에 집중
모든 기술적 결정에는 이유가 있어야 합니다.

**나쁜 예:**
```markdown
Zustand를 사용했습니다.
```

**좋은 예:**
```markdown
Zustand를 상태 관리 라이브러리로 선택했습니다. Redux에 비해 보일러플레이트가
적고, Context API보다 성능이 우수하며, 특히 여러 스토어를 분리하여 관리하기
용이합니다. 프로젝트에서는 확언 목록, 생성된 대화, 앱 설정을 각각 독립적인
스토어로 관리합니다.
```

### 도전과 해결 강조
기술 블로그처럼 문제를 어떻게 해결했는지 상세히 설명합니다.

**포함할 내용:**
- 어떤 문제에 직면했는가?
- 왜 그것이 문제였는가?
- 어떤 해결 방법을 시도했는가?
- 최종적으로 어떻게 해결했는가?
- 해결 과정에서 무엇을 배웠는가?

### 시각적 표현
필요시 다음을 활용하여 이해를 돕습니다:
- 코드 블록 (```언어)
- 인용구 (> )
- 리스트 (-, *)
- 굵게 (**텍스트**)
- 이탤릭 (*텍스트*)

### 톤앤매너
- **객관적이고 전문적**: 마케팅 언어 지양 ("혁신적인", "최고의" 등)
- **솔직하고 진정성 있게**: 실패나 한계도 솔직하게 공유
- **학습 과정 중시**: 완벽한 결과물보다는 과정과 성장에 집중
- **독자 배려**: 전문 용어는 설명 추가, 문맥 제공

## 개인정보처리방침

모바일 앱이나 사용자 데이터를 수집하는 서비스의 경우, `privacy.mdx` 파일을 추가합니다.

### 파일 위치
```
content/projects/project-slug/privacy.mdx
```

### 기본 구조
```markdown
---
title: "개인정보처리방침 - 프로젝트명"
---

**Privacy Policy**

This privacy policy applies to the [앱명] app...
```

### 작성 방법
1. 표준 개인정보처리방침 템플릿 사용
2. 앱 스토어 심사 요구사항에 맞춰 작성
3. 수집하는 정보, 사용 목적, 제3자 공유 여부 명시
4. 연락처 정보 포함

**템플릿 생성 도구:**
- [App Privacy Policy Generator](https://app-privacy-policy-generator.nisrulz.com/)

## 이미지 추가

### 썸네일 이미지
1. 이미지를 `public/images/projects/` 디렉토리에 추가
2. 파일명은 프로젝트 slug와 동일하게 (예: `belief-changer.png`)
3. frontmatter의 `thumbnail` 필드에 경로 지정

```yaml
thumbnail: "/images/projects/belief-changer.png"
```

### 본문 내 이미지
MDX 본문에서 이미지를 사용하려면:

```markdown
![대체 텍스트](/images/projects/프로젝트명/이미지명.png)
```

**권장 사항:**
- 각 프로젝트별로 서브 디렉토리 생성
- 설명적인 파일명 사용
- WebP 포맷 권장 (용량 절감)
- 적절한 크기로 최적화 (1200px 이하)

## 미디어 컴포넌트

MDX에서 이미지, 영상, YouTube를 더 편리하게 삽입할 수 있는 커스텀 컴포넌트를 제공합니다.

### Image 컴포넌트

반응형 이미지를 둥근 모서리와 캡션과 함께 표시합니다.

```mdx
<Image
  src="/images/projects/프로젝트명/이미지.png"
  alt="이미지 설명"
  caption="이미지 캡션 (선택)"
/>
```

**Props:**
| 속성 | 필수 | 기본값 | 설명 |
|------|------|--------|------|
| `src` | O | - | 이미지 경로 |
| `alt` | O | - | 대체 텍스트 (접근성) |
| `caption` | X | - | 이미지 아래 표시되는 캡션 |
| `width` | X | auto | 이미지 너비 (픽셀) |
| `priority` | X | false | 우선 로딩 여부 |

**예시:**
```mdx
## 스크린샷

앱의 메인 화면입니다.

<Image
  src="/images/projects/my-app/main-screen.png"
  alt="앱 메인 화면 스크린샷"
  caption="메인 화면 - 사용자 대시보드"
/>
```

### Video 컴포넌트

로컬 비디오 파일을 반응형으로 표시합니다.

```mdx
<Video
  src="/videos/demo.mp4"
  caption="데모 영상"
/>
```

**Props:**
| 속성 | 필수 | 기본값 | 설명 |
|------|------|--------|------|
| `src` | O | - | 비디오 파일 경로 |
| `caption` | X | - | 비디오 아래 표시되는 캡션 |
| `autoPlay` | X | false | 자동 재생 |
| `loop` | X | false | 반복 재생 |
| `muted` | X | true | 음소거 |
| `controls` | X | true | 컨트롤 표시 |
| `poster` | X | - | 썸네일 이미지 경로 |

**GIF 대체로 사용하기:**
```mdx
<Video
  src="/videos/animation.mp4"
  autoPlay
  loop
  muted
  controls={false}
  caption="로딩 애니메이션"
/>
```

### YouTube 컴포넌트

YouTube 영상을 반응형으로 임베딩합니다.

```mdx
<YouTube
  url="https://www.youtube.com/watch?v=VIDEO_ID"
  caption="영상 제목"
/>
```

**Props:**
| 속성 | 필수 | 기본값 | 설명 |
|------|------|--------|------|
| `url` | O | - | YouTube URL |
| `caption` | X | - | 영상 아래 표시되는 캡션 |
| `aspectRatio` | X | "16:9" | 영상 비율 ("16:9", "4:3", "1:1") |

**지원하는 URL 형식:**
- `https://www.youtube.com/watch?v=VIDEO_ID`
- `https://youtu.be/VIDEO_ID`
- `https://www.youtube.com/embed/VIDEO_ID`

**예시:**
```mdx
## 프로젝트 소개 영상

<YouTube
  url="https://www.youtube.com/watch?v=dQw4w9WgXcQ"
  caption="프로젝트 발표 영상"
/>
```

### 미디어 파일 관리

#### 파일 위치
- **이미지**: `public/images/projects/프로젝트명/`
- **비디오**: `public/videos/프로젝트명/`

#### 권장 사항
- **이미지**: WebP 포맷, 1200px 이하, 용량 최적화
- **비디오**: MP4 포맷 (H.264 코덱), 10MB 이하 권장
- **긴 영상**: YouTube 임베딩 권장 (호스팅 비용 절감)

## 작성 워크플로우

1. **프로젝트 폴더 생성**
   ```bash
   mkdir -p content/projects/your-project-slug
   ```

2. **index.mdx 생성 및 frontmatter 작성**
   ```bash
   touch content/projects/your-project-slug/index.mdx
   ```

3. **본문 작성**
   - 프로젝트 개요부터 시작
   - 기술 스택, 주요 기능 순서로 작성
   - 개발 과정과 결과로 마무리

4. **이미지 추가** (선택)
   ```bash
   cp thumbnail.png public/images/projects/your-project-slug.png
   ```

5. **로컬 확인**
   ```bash
   npm run dev
   ```
   - http://localhost:3000 에서 확인

6. **빌드 및 배포**
   ```bash
   npm run build
   git add .
   git commit -m "feat: your-project-slug 프로젝트 추가"
   git push
   ```
